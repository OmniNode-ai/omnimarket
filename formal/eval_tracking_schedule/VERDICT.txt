Requirements the build answers to
---------------------------------
1. The run id is a function of the window (record, model, cadence, window index), never of the
   send. (M1)
2. The trial driver drops a request for a run id it holds (orchestration/leg.py, and the reducer's
   _run, both "run_already_started"). This is the only thing that keeps a repeated send from a
   second run; the golden chain test goes red with both guards removed. (M2)
3. The driver's row for a run and the run's start are one step. The model's base assumes it; M3
   shows a driver that starts first and records after, and crashes between them, runs twice.
   Residual: whether the orchestrator's emissions and its state_io row flush are one step is a
   runtime property this model does not read. The per-run unit ids are derived from the run id
   (the orchestrator's redelivery tests), so a repeated start names the same units; the first
   window on dev is watched for a second run (ticket risk line).
4. A tick names the window the clock is in, counted from the record's epoch. (M4)
5. A window no tick was in is never run. (M5)
6. Each model reads its own cadence. (M6)
