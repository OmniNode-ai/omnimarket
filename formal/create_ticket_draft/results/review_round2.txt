NEW FINDINGS
N1 CONDITION (fallback alt_stamp_serial only). HandEdit never removes the stamp. If the stamp lives in the
   description text, as the lane stamp does, a person can delete it, and a rerun's search then misses and creates a
   second issue. Scratch variant with EditDropsStamp=TRUE, x_alt_edit_drops_stamp: "Invariant AtMostOneIssuePerCid is
   violated", 9 states: Start FindOk CreateOk HandEdit Crash Start FindOk CreateOk. Under D1 the same knob is harmless
   (x_d1_edit_drops_stamp: no error, 1,631,088 distinct states, P1 + CompletedHasBlock + WrittenCertifiesBlock).
   Fix if the fallback is ever used: keep the stamp in a field that hand editing of the description cannot change
   (a label, an attachment, or a link), and have the search use that field. Alternatively, model the edit as
   dropping the stamp and accept the fallback only if it passes.
N2 CONDITION (a lost edit, inside the stated NOT-MODELLED window). A concurrent duplicate that found the stub before
   the first run's write can write over a human edit that lands after that write. Both runs then complete, and the
   written event certifies the block, with no record that the edit ever happened. Scratch ghost lost (an edit
   overwritten after the issue was written), x_lost_edit_after_write: "Invariant NoLostEdit is violated", 13 states:
   Start FindOk CreateOk ClearOk Build Dup FindOk WriteOk(run1) ClearOk Build HandEdit WriteOk(dup). This matches the
   header's exclusion "a hand edit between a run's find and its write". No ticket property covers it, so it is not
   BLOCKING. Build: (a) no retry or backoff loop between find and write (keep the window to seconds); (b) just before
   the write, re-read and refuse with hand_edited unless the content is the stub or exactly the block built, which
   narrows the window (Linear has no compare-and-set). Record the exclusion in the README. The simpler case, an edit
   of the stub before the first write, is also reachable (x_lost_edit, 8 states) and is the stated "the write wins".
N3 CONDITION (the comparator). Linear normalises markdown (block_sent is not block_norm), so a readback check that
   compares raw text with the rendered build fails EVERY run with hand_edited. In the model the check is a symbol
   comparison. The build must compare the parsed block's fingerprint plus a normalised rendering, and the D1 sandbox
   measurement must include one real write and readback, to show that the comparator accepts Linear's own
   normalisation. The resume path (Cont goes straight to readback) does not build in the model, so the build must
   rebuild deterministically before that comparison (this is round-1 R6, now load-bearing for R1).
N4 NOTE (stale evidence). results/SUMMARY.txt and every results/*.out carry the round-1 model sha (64d3cedf...). For
   example, results/Model.out has 17,025 distinct states, against 1,631,088 now. There is no .out for the new mutants
   (readback_unchecked, conflict_loops, resume_skips_clear, fp_unstable, alt_write_drops_stamp, haz_block_without_event).
   Regenerate results/ against sha f2e5209a before merge. That run may be in progress, as the brief says.
N5 NOTE. The model directory has no README, yet the brief says the two-knob mutants are stated in the README. Add it,
   or move the statement into the .tla header.
N6 NOTE. hand_edited is permanent for a draft: every later retry fails it, and a late failed after a completed is
   reachable (haz_fail_after_complete). Consumers must treat the first completed as authoritative (R7 carry). An edit
   after a run's readback and before its terminal still yields completed. P4 is stated on the read, which is the
   restated P4 the author chose, and that is acceptable.

    from the envelope correlation_id. Test: two envelopes with different correlation_ids and the same draft id make
    one issue.
 B3 (R3) Measure D1 in a sandbox team before merge: a client id in v4 format is accepted; a second create with the

 B4 (R4) One lookup after a refused create; a miss ends with a typed id_unreadable failure; no loop.

 B6 (R6) The build and the fingerprint are deterministic in (request, issue id): no clock, no random. The resume path
    rebuilds. A same draft id with a different payload is refused (idempotency_conflict).
 B7 (R7) The consumer commits only after the terminal publish is acknowledged; a terminal publish error leads to no
    commit, so the message is redelivered. Establish which consumer path the write effect uses (auto-commit=True
    there breaks D8). The first completed is authoritative over a late failed.
 B8 (R8) The write keeps the stamp. Fallback only: a consistent filter (not the search index), and Serial enforced
    across processes and replicas.
 B9 (R9) The written event carries the hash of what the readback returned (title and description) and is published

 B10 (R10, carried) Await the broker ack of ticket-contract-written before the terminal. The event id is
    deterministic in (draft id, issue, fp, hash), and consumers dedupe on it. The written topic is in publish_topics.
 B11 (R11, carried) The description write keeps the caller's first-line lane stamp, and the guard judges the final
    rendered text.
 B12 (N3, new) The readback check compares the parsed fingerprint plus a normalised rendering, with a test that uses
