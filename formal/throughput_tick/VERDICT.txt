What the model says about the tick that runs today (read from the source, MAPPING.txt)
-------------------------------------------------------------------------------------
1. The fill (lab-fill.sent.json) has the lock, the reread under the lock and a record after each
   send in the detached worker: base1 holds for it. Two holes remain, each a mutant that violates:
   (a) fill_lock yields True when the lock file cannot be opened (OSError), so the fill goes on
   without the lock (M4); (b) a worker or tick killed between the runner call and the record
   leaves the key unrecorded, and the next tick starts a second lane, because the lane name
   carries the minute stamp (fill-<kind>-<name>-<YYYYMMDDTHHMM>Z) and the runner refuses only a
   repeated lane name (M5). read_sent also reads an unreadable file as empty (M7).
2. The relaunch (dispatch-replaced.json), stuck-green (green-unlanded.json) and floor
   (floor-escalation.json) stores have no lock and no reread: each decides, sends, then records
   (T1). One launchd tick runs at a time; a second tick (a session's) can overlap it. The floor
   escalation also reads the runner's receipts of its lane prefix before it sends, and stuck-green
   reads the live fix lane; neither read is modelled, so T1 states the exposure of the
   store-only dedupe and not a measured duplicate send.
3. Not seen: any key sent twice inside its 3 h window in the 11 live lab-fill rows read
   (MAPPING.txt). The model finds exposures, not a duplicate that happened.

Requirements for the H3 orchestrator (each is the knob whose removal violates the invariant)
-------------------------------------------------------------------------------------------
R1  Fail closed: a lock or a store that cannot be opened or read sends nothing and says so (M4, M7).
R2  One store and one lock for every writer of the send record, on one state directory
    (the 2026-10-19 incident: two tick state directories, one item sent twice) (M3).
R3  Every send store takes the lock, rereads under it and drops recorded keys before the first
    send (M1, M2, T1); no store of the orchestrator is written without the lock.
R4  The send is idempotent by key: the lane name is a function of the key alone (the whole key
    hashed, not a 60-character cut of it) and the runner returns the lane it already started for
    a repeated key, or the check reads the runner's receipts by key before it sends. Then a crash
    between the send and the record is a retry, not a second lane (M5, base2).
R5  Record after each send (not once after all sends).

Not modelled (UNMEASURED or left out, stated so the pass is not over-read)
--------------------------------------------------------------------------
the dedupe window (a key is sent again after its window by design; the model is one window); more
than two checks; two state directories (R2 states the requirement, the model shares one store); a
store on another host; a refused send (it is not a Send; it is retried by design); the receipt read
of the floor and green paths; the content of a send; the lane-name digest collision (two keys that
agree in their first 60 slug characters share a digest; it can lose a send, it cannot double one).
The state files themselves were not read: see MAPPING.txt.
